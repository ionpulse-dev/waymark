# Knowledge base repository

> **Scope on 2026-11-14:** the current task covers local mode on macOS (Apple silicon) only. This spec is fully in scope. Parts that need server mode stay in this text as a record, and they are not implemented now (see [project decisions](../../../docs/decisions.md)).

## Technical Goal

Define the content repository of a knowledge base: its layout, its shared settings file, and its rules file for agents. One knowledge base is one Git repository, whoever owns it: a company, a team, or one person.

## Dependents

- `create-knowledge-base` and `join-knowledge-base` — create or clone this layout.
- `mcp-server` — reads the shared settings and the limits.
- `project-binding` — the UUID in `.mkbase/waymark.toml` identifies the knowledge base.
- `plain-git-access` — the `AGENTS.md` in the repository root carries the plain-Git rules.

## Deliverables

- The layout of a content repository, with the marker folder `.mkbase` that marks the root of the knowledge base and holds its metadata and configuration (see the [MKBase Document Standard](../../../standard/mkbase-1.0.md)).
- The schema of `.mkbase/waymark.toml`.
- The templates for `.mkbase/waymark.toml` and `AGENTS.md`.
- The Obsidian vault settings and Git ignore rules that `init` writes (the `init` tool, see `create-knowledge-base`).

## Scope

**In scope:**
- Files in the repository root and the `knowledge/` tree, whose root folder is marked by the folder `.mkbase`.
- Teams as folders, if the organization chooses to.
- Shared settings. Personal settings are specified in `join-knowledge-base`.

**Out of scope:**
- The format of one document (see `document-format`).
- The tooling repository. The content lives in a separate repository per knowledge base.

## Constraints

- The Git remote is private and belongs to the owner of the knowledge base.
- Everyone with read access to the repository sees every document. Git has no read permission per folder. One repository has one audience.
- The repository holds no secrets and no personal settings.

### Layout

```text
<slug>-knowledge-base/        (cloned to ~/Projects/<slug>-knowledge-base by default)
  AGENTS.md                   rules for agents
  .obsidian/app.json          Markdown links and relative paths as defaults
  .gitignore                  .obsidian/* except .obsidian/app.json
  knowledge/                  root of the knowledge base
    .mkbase/                   marker folder: metadata and configuration, committed
      version                 version of the document standard, for example 1.0
      waymark.toml            shared settings of waymark
    backend/
      payments/
        idempotency-keys.md
```

- The lock and the sync state are in `.git/` of the clone (for example `.git/waymark.lock`). Git never commits `.git/`, and Obsidian never sees it. The content repository has no `.waymark/` folder.
- `AGENTS.md` is allowed in the repository root, outside the knowledge base.
- The `init` tool writes the marker folder `knowledge/.mkbase/` with the file `version`. The folder that contains `.mkbase/` is the root of the knowledge base. The ID of a document is its path below that root. The marker folder is defined by the MKBase Document Standard and is not specific to waymark.
- Everything that describes or configures the knowledge base lives in `.mkbase/`. waymark keeps its shared settings in `.mkbase/waymark.toml`. Other tools may keep their own files there. waymark keeps its local state (lock and sync status) in `.git/`, because the state is never committed.
- **The organization builds the tree.** waymark has no built-in folders. The folder structure may mirror the team structure if the organization decides so. waymark does not care. A knowledge base can add a `shared/` folder. It is a normal folder.
- **No `owners` field.** The author is in Git history, with name and email.
- Reorganizations use `move-documents`.

### `.mkbase/waymark.toml` (shared settings)

```toml
schema = 1                      # version of this file format, written by init
name = "Example Company"        # asked by init
id = "<uuid>"                   # generated by init, identifies the knowledge base
slug = "example"                # default folder ~/Projects/example-knowledge-base
verification = false            # true: owners verify documents

[limits]                        # shared limits, see trust-model. Every key is optional.
access = "read-write"           # read-only | read-write
tools_denied = []               # for example ["delete", "move"]
folders = []                    # allowed folder globs, empty = all
max_results = 5
max_tokens = 800
max_documents_opened = 20       # per session

[approval]
required_for = []               # tool names, or "write"
via = "elicitation"             # elicitation | console

[people]
email_domains = []              # optional allowed author domains
email_blocklist = []            # extra blocked parts

[documents]
max_bytes = 102400
title_max_words = 15
description_max_words = 50

[lint]
extra_secret_patterns = []      # regular expressions
```

**Schema version.** The key `schema` is a whole number of 1 or more. It is the version of the format of this file. A file without the key has schema 1. Every build of waymark knows the highest schema that it supports (now 1). If the file has a higher schema, the server refuses every tool except `status`, with the error `setup_problem`, the message "This knowledge base needs a newer waymark. Its settings file has schema N, and this waymark supports schema M.", and the `next` sentence "Update waymark with `brew upgrade waymark`, then restart your agent tool." `status` shows the same problem and both numbers, so a person can see why the tools fail. This holds for reads too: nobody works on a file that an older waymark might read wrongly. A `schema` that is not a whole number of 1 or more is a `setup_problem`. A build never raises the schema by itself. There is no migration yet. The number is raised only by a later release that needs a change of this file, and only through a deliberate step of the owner (a normal commit that `undo` can revert). The check protects only builds that contain it: waymark 0.1.2 and older ignore the key, so the number is not raised before the team had time to update.

The shared file holds no behavior rules. There is no read level, write level, or agent tool list. Behavior is written in the `AGENTS.md` of the team.

## Versions and updates

This section is the one place that says how a knowledge base and the waymark binary stay compatible over time. Other documents link here.

### The versions

| What | Where it lives | Today | Checked by waymark |
|---|---|---|---|
| Program version | the binary (`waymark --version`) | 0.1.x | no, it is information |
| Settings schema | `schema` in `.mkbase/waymark.toml` | 1 | yes: a higher number blocks every tool except `status` |
| Document standard | `.mkbase/version` and `standard/mkbase-1.0.md` | 1.0 | no. Nothing reads `.mkbase/version` yet (see `todo.md`) |
| Tool interface | the tool descriptions that the binary sends at the start of a session | follows the program version | not stored anywhere, so it needs no migration |

The repository holds the data and its two version labels. The binary holds the highest schema it supports and compares the two at every call. There is no database, so the only stored formats are the documents and the settings file.

### Two kinds of update

| Kind | What it is | Who decides | State |
|---|---|---|---|
| **Repair** | Adds what is missing in the settings file (for example the key `schema`). Never changes a value that exists. Safe to run twice. Older builds can still read the result. | Automatic | implemented |
| **Migration** | A change of the format that older builds cannot read (schema 1 to 2, 2 to 3, and so on). | The owner, by a deliberate step | designed, not built (no schema 2 exists) |

### Automatic repairs

- The repairs are a list in the binary (`src/kb/repairs.rs`). Each one takes the text of the settings file and returns the fixed text, or nothing if the file needs nothing.
- A repair runs at the first call that writes: a write tool, with read-write access, not paused, and not a preview. A read, a preview, and a call under read-only access never repair. No approval is asked, because a repair adds only keys that the binary defines.
- It goes in its own commit before the change of the caller: `waymark: repair "settings"`, under the author of the person, and it is pushed with that change. `undo` can revert it. The result of the call has a notice, for example "Repaired the settings file: added the missing schema key."
- A repair never touches `[limits]`, `[approval]`, or any value that the owner set. It comes only from the list in the binary, never from the input of a tool or from a document. An agent cannot use it to loosen a limit.
- Two people who trigger the same repair at once are handled by the write flow of `git-sync`: it fetches first, so the second finds the file fixed and does nothing.
- The first repair: a file without the key `schema` gets `schema = 1` as its first line. Every other line stays as it was, with its comments.

### Migrations (designed, not built)

- One small function for each step: 1 to 2, 2 to 3, and so on. A file at schema 1 and a binary that supports 4 run three steps in order. A step takes the text of version N and returns the text of version N+1. It is pure (no Git, no network), safe to run twice, and keeps comments (it edits text in place, for example with `toml_edit`).
- Each schema has a sample file in the tests, and one test runs the whole chain.
- A migration never runs on a read or on its own. It is a tool, `migrate`, that is listed only when the file has an older schema than the binary supports (like the verification tools), so it costs no context otherwise. `status` and a notice tell the owner that a migration is available. It is a normal write: one commit under the author, `preview`, approval rules, and `undo`.
- A newer binary reads the previous schema as it is, until the owner migrates, so one person who updates waymark does not lock the team out. After the migration, older builds are blocked by the rule for a higher schema.
- The rule that tools never change this file has two exceptions, both from code in the binary and not from input: the repairs and `migrate`.
- If steps are dropped one day, a file that is too old gets the message "Open this knowledge base once with waymark X to migrate it first."
- The check for a higher schema must ship before the first schema bump, because builds without it ignore the key. Releases up to 0.1.2 do. The number is not raised before the team had time to update.

### Updates of the MCP entry

The entry of the agent tool belongs to the person. If an update needs a different entry (a removed argument, a new required one), waymark still starts and shows the problem and the fix in three places. The rules are in `mcp-server`, section "Updates of the MCP entry".

### The start of a session

`initialize` checks the settings file when it builds the `instructions` text. A schema problem is in that text. The text is not enough on its own, because a client may not show it, so every tool call also fails with the same message. A migration is never run during `initialize`: it must not write, and it must not wait for the network.

### A file that cannot be read

A settings file with no `id` (or one that is not valid TOML) blocks every tool, so no repair can run. The error tells the person to fix the file by hand and commit it. `init` does not repair an existing settings file.

## Acceptance Criteria

- **Given** a new repository from `init`, **When** it is opened in Obsidian, **Then** it opens as a vault and new links use Markdown links with relative paths.
- **Given** a repository, **When** `git status` runs after Obsidian was used, **Then** personal Obsidian files do not show as changes.
- **Given** a `.mkbase/waymark.toml` without `id`, **When** the server reads it, **Then** the server reports `setup_problem`.
- **Given** a `.mkbase/waymark.toml` with a `schema` higher than the build supports, **When** any tool except `status` runs, **Then** it fails with `setup_problem` and the message "This knowledge base needs a newer waymark", and `status` shows the file's schema, the supported one, and the fix.
- **Given** a file without `schema`, **When** the server reads it, **Then** it works as schema 1.
- **Given** a `schema` of 0, a negative number, or a text, **When** the server reads it, **Then** it fails with `setup_problem`.
- **Given** a new repository from `init`, **When** `waymark.toml` is read, **Then** it has `schema = 1`.
- **Given** a settings file without `schema`, **When** a write tool runs, **Then** `schema = 1` is added as its first line in a commit `waymark: repair "settings"` before the commit of the write, every other line is unchanged, and the result has a notice.
- **Given** a settings file without `schema`, **When** a read tool runs or a write runs with `preview: true`, **Then** nothing is committed.
- **Given** a current settings file, **When** a write tool runs, **Then** no repair commit is made.
- **Given** a settings file with values in `[limits]`, **When** a repair runs, **Then** those values and the comments are unchanged.
- **Given** a shared limit and a looser personal value, **When** the server reads both, **Then** the stricter value applies.
- **Given** a folder reorganization, **When** it is done through waymark, **Then** no `owners` field or team list needs an update.
