# Knowledge base repository

> **Scope on 2026-11-14:** the current task covers local mode on macOS (Apple silicon) only. This spec is fully in scope. Parts that need server mode stay in this text as a record, and they are not implemented now (see [project decisions](../../../docs/decisions.md)).

## Technical Goal

Define the content repository of a knowledge base: its layout, its shared settings file, and its rules file for agents. One knowledge base is one Git repository, whoever owns it: a company, a team, or one person.

## Dependents

- `create-knowledge-base` and `join-knowledge-base` — create or clone this layout.
- `mcp-server` — reads the shared settings and the limits.
- `project-binding` — the UUID in `.mkbase/waymark.toml` identifies the knowledge base.
- `plain-git-access` — the `AGENTS.md` in the repository root carries the plain-Git rules.

## Deliverables

- The layout of a content repository, with the marker folder `.mkbase` that marks the root of the knowledge base and holds its metadata and configuration (see the [MKBase Document Standard](../../../standard/mkbase-1.0.md)).
- The schema of `.mkbase/waymark.toml`.
- The templates for `.mkbase/waymark.toml` and `AGENTS.md`.
- The Obsidian vault settings and Git ignore rules that `init` writes (the `init` tool, see `create-knowledge-base`).

## Scope

**In scope:**
- Files in the repository root and the `knowledge/` tree, whose root folder is marked by the folder `.mkbase`.
- Teams as folders, if the organization chooses to.
- Shared settings. Personal settings are specified in `join-knowledge-base`.

**Out of scope:**
- The format of one document (see `document-format`).
- The tooling repository. The content lives in a separate repository per knowledge base.

## Constraints

- The Git remote is private and belongs to the owner of the knowledge base.
- Everyone with read access to the repository sees every document. Git has no read permission per folder. One repository has one audience.
- The repository holds no secrets and no personal settings.

### Layout

```text
<slug>-knowledge-base/        (cloned to ~/Projects/<slug>-knowledge-base by default)
  AGENTS.md                   rules for agents
  .obsidian/app.json          Markdown links and relative paths as defaults
  .gitignore                  .obsidian/* except .obsidian/app.json
  knowledge/                  root of the knowledge base
    .mkbase/                   marker folder: metadata and configuration, committed
      version                 version of the document standard, for example 1.0
      waymark.toml            shared settings of waymark
    backend/
      payments/
        idempotency-keys.md
```

- The lock and the sync state are in `.git/` of the clone (for example `.git/waymark.lock`). Git never commits `.git/`, and Obsidian never sees it. The content repository has no `.waymark/` folder.
- `AGENTS.md` is allowed in the repository root, outside the knowledge base.
- The `init` tool writes the marker folder `knowledge/.mkbase/` with the file `version`. The folder that contains `.mkbase/` is the root of the knowledge base. The ID of a document is its path below that root. The marker folder is defined by the MKBase Document Standard and is not specific to waymark.
- Everything that describes or configures the knowledge base lives in `.mkbase/`. waymark keeps its shared settings in `.mkbase/waymark.toml`. Other tools may keep their own files there. waymark keeps its local state (lock and sync status) in `.git/`, because the state is never committed.
- **The organization builds the tree.** waymark has no built-in folders. The folder structure may mirror the team structure if the organization decides so. waymark does not care. A knowledge base can add a `shared/` folder. It is a normal folder.
- **No `owners` field.** The author is in Git history, with name and email.
- Reorganizations use `move-documents`.

### `.mkbase/waymark.toml` (shared settings)

```toml
name = "Example Company"        # asked by init
id = "<uuid>"                   # generated by init, identifies the knowledge base
slug = "example"                # default folder ~/Projects/example-knowledge-base
verification = false            # true: owners verify documents

[limits]                        # shared limits, see trust-model. Every key is optional.
access = "read-write"           # read-only | read-write
tools_denied = []               # for example ["delete", "move"]
folders = []                    # allowed folder globs, empty = all
max_results = 5
max_tokens = 800
max_documents_opened = 20       # per session

[approval]
required_for = []               # tool names, or "write"
via = "elicitation"             # elicitation | console

[people]
email_domains = []              # optional allowed author domains
email_blocklist = []            # extra blocked parts

[documents]
max_bytes = 102400
title_max_words = 15
description_max_words = 50

[lint]
extra_secret_patterns = []      # regular expressions
```

The shared file holds no behavior rules. There is no read level, write level, or agent tool list. Behavior is written in the `AGENTS.md` of the team.

## Acceptance Criteria

- **Given** a new repository from `init`, **When** it is opened in Obsidian, **Then** it opens as a vault and new links use Markdown links with relative paths.
- **Given** a repository, **When** `git status` runs after Obsidian was used, **Then** personal Obsidian files do not show as changes.
- **Given** a `.mkbase/waymark.toml` without `id`, **When** the server reads it, **Then** the server reports `setup_problem`.
- **Given** a shared limit and a looser personal value, **When** the server reads both, **Then** the stricter value applies.
- **Given** a folder reorganization, **When** it is done through waymark, **Then** no `owners` field or team list needs an update.
